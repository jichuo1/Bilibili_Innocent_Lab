# 阶段 5：启动关键路径优化设计

范围归属复核：本阶段是已获授权的启动性能扩展，主要候选为公共适配/反射/安装工作的裁减，实际实现限定于 NPatch。测到 NPatch 下的开销不单独证明它由 NPatch 引入；实际收益、兼容约束和技术归属分别见[全目录范围复核](npatch-scope-audit.md#已做但必须拆分归属的增强)。

设计日期：2026-10-23；设计源码基线：`45f18269`，分支 `feat/npatch-compat`。5.1–5.5 已按限定实测范围完成；实际结果见[实施与证据](npatch-stage5-performance-results.md)，排期以[路线图](npatch-implementation-roadmap.md)为准。本文保留原设计目标；Manager 默认组达到期望，embed 实际减少 17.57%，未达 20%，以实施证据为准，不修改目标或外推未测组合。

## 1. 目标与范围

保留当前许可与功能覆盖，减少 NPatch Manager/embed 启动时模块在主线程上的同步工作，同时避免把卡顿转移到第一次打开视频、评论或 Web。优先优化正常进程冷启动的已有适配缓存命中路径；首次适配、重修补、子进程和异常授权分别验证。

本阶段交付分段证据、由证据支持的优化和前后对照。旧 F6 的“读取上次许可直接安装、后台再授权”和子进程跳过独立授权继续撤回；不承诺全部 Hook 在 300ms 内安装，不通过缩短授权窗口制造更快的失败，也不以功能减少换取耗时下降。

不扩展到 loader 大改、DexOpt 引导、全量热重载、视觉引擎冻结、通用功能适配或全部业务矩阵清零。若证据主要指向 loader/宿主/系统，明确拆出耗时与后续议题，不把它记成 Hook 优化收益。

## 2. 当前源码支持的判断

| 观察 | 对设计的影响 |
|---|---|
| `HookEntry.authorizeAndInstall` 从 `Application.attach.before` 同步进入，`callApplicationOnCreate.before` 兜底；主进程失败后可在首次恢复时再试一次 | 授权和早期 Hook 存在调用期限；不能把整个入口直接异步化 |
| NPatch 已跳过标准框架的 Remote Preferences 前置查询；`HostAdmissionClient` 已并发 provider/binder/local，按现有条件补广播 | 不重复实施“去 Manager 前置读取”或“授权通道并发”；不预设授权仍固定阻塞 2 秒 |
| `installAuthorizedHooks` 的 `hostAdaptResult` 虽为 lazy，主进程发布适配诊断及安装器引用会求值；`quickLocate` 仍遍历多类能力并构造诊断/结构指纹 | 按配置和进程缩小定位需求是候选；lazy 本身不能证明工作已省略 |
| 当前启动缓存已校验安装指纹、版本与重置；实时定位优先，已校验缓存只补缺口 | 优化必须保持此优先级，不能改成缓存覆盖实时结果；阶段 3 的原版 DEX 后台复用继续保留 |
| `FeatureInstallCoordinator` 顺序安装并隔离单项失败；自由复制等仍有存量安装块和独立重试 | 只在 coordinator 计时会漏掉工作；先覆盖存量边界，再决定是否拆分 |
| `KavaMemberLookup` 已缓存指定 ClassLoader 的 Class、Member、集合及负查询，已有命中/失败计数 | 复用现有缓存并量测增量，不另造反射缓存；不能把本来已有的能力当成新收益 |
| 部分安装器内部已判断 `non-main-process`，但共享准备和参数求值可能早于该判断 | 子进程先审计准备依赖；不能看到主进程专用功能就跳过整个子进程安装链 |
| `ensureAdapted`、适配后补安装、漫游 attach 和日志汇总与初始安装链相邻；源码说明需避免实时定位与后台适配并发 | 改动要区分同步准备、提交后台和后台实际执行，保留既有相对时序 |

来源为当前仓库的 `hook/HookEntry.kt`、`hook/VersionAdapter.kt`、`hook/feature/FeatureInstaller.kt`、`hook/HookPointRegistry.kt`、`runtime/KavaMemberLookup.kt`、`runtime/HostAdmissionClient.kt` 和 `runtime/HostAdmissionRoutePlan.kt`，路径均相对于 Android 主源码包。

历史数据仅用于确定调查方向：[B5 对照](npatch-compatibility-plan.md)曾记录同机首帧中位数 11.417s（无模块）、12.564s（仅加载且关闭）、14.544s（正常开启），正常开启 Hook 链约 2000ms，授权 30–42ms；阶段 4.1 单次记录为授权 253ms、安装 2153ms。二者配置、产物和采样不同，不拼成当前基线，也不从这些总数推断某个安装器最慢。`quickLocate` 旧注释里的“~1ms”不作为当前全链测量。

## 3. 必须保持的行为

1. 每个需要功能 Hook 的 NPatch 进程独立取得当前端点许可；保留 UID、nonce、challenge、terms、fingerprint、lease、revision 和关闭终态的既有校验。适配缓存不成为许可来源，主进程结果不成为子进程凭据。
2. 未获准、关闭和条款拒绝时不安装功能 Hook。只读诊断、存活探测和既有生命周期 bootstrap 的角色不扩大；测量不触发功能安装或主动加载 native。
3. 不改变标准框架的来源优先级与已验证回退。共享代码改动必须补标准框架行为回归，不能只用 NPatch 测试证明兼容。
4. 保持已有首次调用覆盖、失败隔离、重复注册防护及有边界的适配补安装；不新增“早期漏掉，下一次操作再生效”。重试不是新的进程启动，单个安装器失败不能截断后续项。
5. 后台只传不可变配置/纯数据及必要的应用级依赖；进程缓存不保存 Activity/View/宿主业务实例。宿主成员定位继续使用 `KavaMemberLookup` 和现有封装，保持 ClassLoader、重载与继承边界。
6. 保留当前安装状态与叶项证据语义。排队、构造对象、解析成功和提交后台均不能标记安装成功。若候选确需延迟功能安装，必须先独立设计部分完成状态、许可有效性和安装截止条件，本方案默认不采用。

## 4. 测量设计：先找出时间花在哪里

### 4.1 初始采集边界

5.1 使用 DEBUG 可启用的进程内测量器，默认不向现有生产协议加字段。入口准备及每次授权尝试分别最多 128 条固定 ID 记录，最多保留 2 次尝试，超限只递增丢弃数；该容量不改变现有重试次数。采集溢出时不能把不完整热点表当完整归因。不在启动期写文件或执行跨进程测量上报。测试在启动结束后通过独立 DEBUG 只读入口取回快照，再写入 `captures/npatch-stage5/`；入口沿用现有签名权限、本次 nonce 与当前安装身份校验，不携带许可材料，不并入 v4 生产响应，Release 不注册。

| 层级 | 边界与内容 |
|---|---|
| 入口准备 | 模块入口至注册 bootstrap 的同步准备；授权函数入口至 admission 起点的档案解析、诊断初始化和配置分支，单独计量 |
| 授权 | 保留现有 admission 起止与选中通道；不为追踪重发请求、不等待原本未消费的迟到结果 |
| 适配准备 | `readStartupCache`、`quickLocate` 内各能力家族、诊断/结构指纹、实时与缓存合并；记录缓存状态的固定分类 |
| 安装 | coordinator 的每个父安装器，以及自由复制、漫游 attach 等存量块；区别跳过、成功、部分、异常 |
| 定位与注册 | 共用定位/注册边界的总耗时、次数和 Kava 计数增量；优先粗粒度，最慢项再细分，不记录每次回调 |
| 附属工作 | 诊断汇总、日志格式化、适配任务提交与实际后台执行分开；后台与主线程重叠不能相加 |
| 生命周期 | attach bootstrap 返回、Application 初始化返回；前台重试独立编号，注明安装发生在哪个边界 |

耗时使用单调时钟；固定 ID、耗时、计数、线程类别和结果枚举即可，不收配置值、宿主成员名、业务正文或凭据。父子段保留层级：父段含子段，报告列出包含耗时与扣除同线程子段后的自身耗时，不能把它们全部求和；跨线程段独立呈现。模块同步总时长按主线程模块工作区间的并集计算，包含同步等待，不是 CPU 时间。失败也在 finally 封口；未执行为未采集，不能填 0 当成功。未覆盖的剩余时间单列，最多展示最慢 10 项，但原始有界段保留以供核对。

现有 `NPatchStartupEvidence.totalMs` 仍为 admission + install，不含整个模块入口、宿主冷启动或首帧；HookEntry 日志中的授权准备总时长也有自己的边界。新增测量不得重解释旧字段。阶段 4 的查询 v4、支持 schema 1、主诊断 schema 3、报告格式 7 保持原样；如后续确需产品化细分面板，另开有严格编解码和兼容策略的协议单元，不作为性能优化前置。

### 4.2 对照方法与收益标准

- 固定源码、模块/宿主 APK 哈希、修复版 Loader、签名、模式、系统/ABI、配置身份和缓存状态。基线与候选使用相同详细采样开关，额外以关闭采样的产物确认测量器没有主导结果。
- 每种模式先预热并排除预热数据；有效缓存下，基线与最终候选各至少 10 次进程冷启动，以小批次交替取样。每次切换产物均核对设置 App/内嵌代码一致，排除升级首启，确认原版 DEX 审核/缓存重绑定完成且下次启动稳定命中后才进入该批。这里的冷启动是停止并重新启动宿主进程，不清数据、不清系统缓存、不强制编译、不重启手机。
- 默认配置是主性能组；另冻结一个涵盖实际已支持早期 Hook、复制、首页过滤、播放器/Story 的组合配置，基线/候选在每种模式各至少 5 次。保留同一组开关，不能让候选悄悄少装功能。首次适配和重修补分别记录，不混入稳定缓存组。
- 通过明确 MAIN Activity 启动；每轮确认新进程、当前配置许可和缓存分类，取样完成后再查询诊断，避免查询干扰启动。记录授权/安装、模块同步耗时、真实首帧和首页可交互时间；首帧与交互证据独立于安装日志。若系统首帧信息缺失，则缺失并保留有界观察记录；`am start -W` 超时不能当作首帧值，也不能静默删掉失败样本。
- 原始样本、排除原因、失败次数和顺序全部保存，报告中位数、最近秩 p90 与范围；10 个样本的 p90 只作小样本比较，不外推长期分布。设备热状态或网络内容显著不一致时标记该批不可比，重新成对采集，不只补候选的好样本。

5.1 在采样前固定首帧和可交互的判据：系统首帧仅表示启动 Activity 首次绘制，开屏结束后的首页可见/固定操作可响应另以相同录屏或测试观察方法计时，注明精度与截止时间；不拿网络内容全部加载完成作交互判据。首次视频/评论/Web 操作也按相同动作记录等待，识别被转移的首用卡顿。

**期望收益**：默认配置每种模式的模块启动同步耗时中位数，相对 5.1 基线降低至少 20% 且至少 150ms。这是调查目标，不是已验证承诺；5.1 完成后记录可优化占比及是否可达，不能事后换配置或改指标凑目标。

**保留改动的条件**：对应热点下降可复现，主线程同步总时长和真实交互没有把收益抵消，首次功能覆盖不退步。若最终某模式的同步耗时或首帧/交互中位数增加超过 `max(基线的 5%, 100ms)`，或 p90 出现同量级回退，需复测并解释；未解释前不作为通过。阈值以下仍检查是否有持续退化，不能称为必然无影响。若达不到期望收益，如实交付实际改善、瓶颈和未达原因；只有观测性改动时只能报告定位完成，不能报告性能优化完成。

无模块/免 Root 关闭的历史对照可以帮助归因，新的主要比较采用同模式、同功能的优化前后产物。关闭态不包含正常 Hook 工作，不能直接当作候选性能成绩。

## 5. 优化顺序与具体决策

### 5.2 按当前进程和配置准备适配结果

首选候选是减少不需要的定位，而不是推迟必需注册。引入启动局部的能力需求集合（设计概念，具体类型名在实施时确定）：由已获准的不可变配置、进程角色和共享依赖推导；同一能力家族最多定位一次，各消费者复用结果。

- 将 `quickLocate` 的家族定位和诊断构造按需拆开。需求是消费者依赖的并集，不能只检查同名开关：例如复制与评论拓扑共享路径、普通/Story 画质、首页相关结构和后台适配补安装都要纳入。
- 保持“实时结果优先，已校验缓存补位”；未知依赖或未迁移家族默认沿用原路径。只裁掉有证据的无消费者工作，不先批量改所有定位器。
- 诊断不能为了展示所有适配点又强迫执行全部定位。未探测明确表示未探测，不能计为缺失/失败或成功；若现有表达不足，先保持该部分原路径，不能伪造结果。
- 按需结果仅用于当前启动的安装，不把不完整结构当作全量适配缓存写回。不改变规则/schema 来绕过完整性校验；`ensureAdapted` 的全量结果、原版 DEX 审核和手动重置语义继续独立成立。
- 默认不让实时定位与后台全量适配新增并发。先完成必要的启动定位/注册，再沿既有边界调度适配，避免对尚未证明线程安全的缓存和状态做并行化。

是否实施、先拆哪些家族由 5.1 的自身耗时和消费者审计决定；若它不是主要热点，就记录排除结论并先处理实际热点。

### 5.3 共享准备与子进程开销

逐项检查昂贵参数是否在安装器内部的 `disabled/non-main-process` 返回之前已被求值；把确定无需的对象构造和定位放到相应门控之后。复用启动局部缓存快照与已解析 Member，避免多次 JSON 读取、同族重复枚举和重复格式化；保留已有 Kava 缓存，不引入跨 ClassLoader/跨安装的 Member 复用。

进程表从真实安装器和共用 Hook 推导，覆盖主进程、`:web`、`:download`、`:ijkservice`，未知进程保留原策略。逐进程列出“仍需要的 Hook/依赖”和“可省的主进程专用准备”，禁止仅凭进程名称创建整进程禁用表。子进程使用现有业务动作按需启动，不为性能报告人为唤醒所有进程。

本单元不共享或持久化授权，不合并不同进程的 challenge/lease，也不删除前台单次重试。若新测量发现授权异常，仅对可复现的具体等待/调度问题另做小修，保持现有超时、拒绝优先级和来源契约；不再次整体重写 IPC。

### 5.4 按首次调用期限决定是否后移

5.4 是有条件单元；若同步去重已达到目标，或没有安全且有收益的候选，可以以证据说明无后移改动。默认所有功能 Hook 仍在原安装边界内注册。

| 工作类别 | 默认处理 | 改动需要的证据 |
|---|---|---|
| 开屏/首屏响应、初始化、共享复制及 Web 相关 Hook | 当前许可后同步注册 | 实际最早调用点、入口依赖和直接冷启动目标页面；不能按“功能看起来不常用”后移 |
| Hook 回调所需的成员与数据 | 注册前准备，或沿已验证的现有惰性路径 | 首次调用不缺失、无显著首用阻塞、不重复定位和注册 |
| 纯诊断格式化、汇总和非业务预热 | 实测有占比时评估后台合并 | 不改变真实安装结果、回执新鲜性、异常 handler 接入期限或应答能力；输出不可变快照 |
| 后台 DexKit、原版 DEX 校验、适配后补安装 | 保留现有独立路径并检查竞争 | 不推迟必要补安装、不新增 attach 同步 APK I/O、不改变缓存重绑定与下次命中 |
| 与 UI/生命周期相关的工作 | 保持现有线程与生命周期 | 不能仅以 `post` 或“Application 已返回”为安全证明；需确认目标工作尚未发生且宿主语义允许 |

不新增常驻线程池或无界队列；适合后台的纯任务优先复用现有有界执行器并经 `HostThreadGuard` 保护。不能占满授权/回执的执行器，不能把耗时任务整体排到主线程下一帧。不能让异步日志、诊断或预热失败拖垮宿主或修改功能状态。

## 6. 实施单元及出口

| 单元 | 具体交付 | 退出条件 |
|---|---|---|
| 5.1 分段测量与基线 | DEBUG 有界测量器、可重复采集方式、主/子进程依赖表、最慢项和时序表 | 双模式默认/组合有效基线；测量覆盖 coordinator 外工作且能解释剩余时间；选出有占比的候选，不先改调度 |
| 5.2 按需适配 | 已审计家族的需求集合与启动局部复用；其余保留原路径 | 对应定位次数下降；实时/缓存优先级、关闭/未知、共享依赖、重置/缓存缺失测试与首次行为通过 |
| 5.3 共享准备与进程优化 | 实际热点的去重/门控前移，逐进程保留表 | 子进程新鲜许可、共用 Hook 和真实 Web/下载/播放服务路径保留；无整进程裁剪，收益独立记录 |
| 5.4 有条件后移 | 有收益且时序允许的附属工作，或附证据的无需后移结论 | 首次调用和线程/生命周期证据通过；安装状态、回执及适配补安装不提前报完成 |
| 5.5 最终对照 | 相同功能配置的双模式性能表、回归结果、支持文档/路线图回填 | 所有保留改动通过功能和适用门禁，报告实际收益及未测范围，不用旧约 2 秒替代新基线 |
