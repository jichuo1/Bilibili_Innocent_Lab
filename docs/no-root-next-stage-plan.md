## 阶段 8：Shizuku

首个交付目标沿用 F11 的宿主重启需求：**保存当前配置 → 检查服务并取得用户授权 → 强停目标宿主 → 重新拉起 → 根据新进程及当前配置回执判断结果。** 不把命令返回成功等同于 Hook 已加载或配置已生效。

实施前先核对现有公共重启/启动封装、依赖目录、目标版本的官方文档和本机可用组件，再确定 SDK 版本与服务接入方式。实际启动身份、UID 和可用权限需现场确认，不固定假定为 shell 2000，也不因存在服务就认为已获授权。

首期范围：

- 明确区分未安装、服务未启动、未授权、拒绝/撤销、可用和服务断开；只在用户操作时请求所需授权。
- 经现有发布/停用落盘屏障保存状态，仅操作已声明的目标宿主。保留当前配置身份、条款、关闭状态和运行回执的原语义。
- 强停后核对旧进程退出，再执行受控启动；当前有效回执只证明对应配置的实际结果。启动失败、授权失败、回执超时分别呈现，避免误报“重启完成”。
- 处理 Binder/服务死亡、重连、设置 App 生命周期和重复点击，避免迟到请求触发额外重启。
- 无授权或服务不可用时，保留阶段 6 已交付的系统详情/手动强停/打开并验证路径；Root 原路径继续回归。

验收覆盖正常操作、用户拒绝、授权撤销、服务停止/死亡、取消、重复操作、保存失败、强停/启动失败、旧回执拒绝及当前回执确认。先在既有 NPatch Manager/embed 上验证；之后将可复用重启入口纳入阶段 9 的框架对照。

此次排期不自动包含 DexOpt、任意 shell 命令面板或其它特权管理功能。需要这些能力时按具体需求另行评估。

## 阶段 9.1：LSPatch

最初的问题来源为用户转述“有人反馈支持不佳”；实施时用户提供了 [issue #31](https://github.com/jichuo1/Bilibili_Innocent_Lab/issues/31)。已按实际 JingMatrix LSPatch 1.2（487）、B 站 9.13.0 及本地/集成模式构造基线，复现准入拒绝并完成修复；原输入、操作与支持范围见[阶段 9 记录](lspatch-stage9.md)。不能将该组合的结论外推到所有 LSPatch 或 NPatch。

现有源码提供两个调查起点：

- `settings/remote/ModernFrameworkStatus.kt` 已有精确 LSPatch 名称识别，并将其标准发布与 NPatch 免 Root 通道区分。
- `runtime/compat/CompatibilityManagerProbe.kt` 已有 LSPatch 服务探测/请求回推边界；请求已排队不等于 SDK 服务已连接，也不证明宿主配置生效。

这些只是已有实现依据，不是当前框架版本或完整业务已兼容的证明。调查逐项记录：

1. 框架项目/分支、版本、来源、管理器与修补工具、APK 哈希、Android/ABI、宿主/模块版本及实际修补参数；框架身份、管理器安装与宿主加载分别核对。
2. 实际支持的模块入口/API、作用域与加载方式、配置交付和存储、服务连接/回推、主进程及适用子进程。具体模式按该版本核实，不预设与 NPatch 相同。
3. 冷启动、配置修改、启停/条款、当前授权/回执、管理器或设置 App 不可达、模块更新与重新修补、数据保留及恢复。
4. Web、复制、播放器、账号/下载与分享的必要代表性回归。通用业务缺陷继续独立归属；重签名接收方和修补宿主两个维度分列，账号内流程沿用既有后排决定。
5. 按实际失败阶段区分注入、框架 API/配置服务、模块授权、宿主适配和第三方接收；仅修复已确认问题，保持 UID/nonce/条款/租约等边界，不强制伪造成功。

完成条件：产物与环境可复现，反馈能复现或明确写出未复现的对照范围；已确认阻塞得到修复与原路径复测；支持范围和恢复步骤有依据；共享代码修改回归已完成的 NPatch 组合及标准框架契约。未知版本和未覆盖业务保持未验证。

## 阶段 9.2：其它免 Root 框架

与 LSPatch 调查一并建立清单，覆盖实际发现的 LSPatch 衍生/分支、其它 APK 修补加载方案，以及容器/虚拟化等不同形态。**具体项目名称、维护状态、版本、接口和可获取产物在执行调查时核实**，不凭“免 Root”名称或项目关联推定兼容。

每个候选至少记录：

| 信息 | 要回答的问题 |
|---|---|
| 项目身份与来源 | 实际项目/分支是什么，版本及来源是否可核对，是否有可复现产物 |
| 技术形态与模块 API | 是 APK 修补还是容器等方式，模块入口/API 能否满足当前模块要求 |
| 配置/身份模型 | 如何交付配置，服务是否真实连接，宿主 UID/包/进程及回执身份如何观察 |
| 安装与生命周期 | 模块更新、管理器失联、子进程、重新修补及恢复如何工作 |
| 证据与优先级 | 仅资料调查、可测试、已测试、已复现问题、确认不满足条件或仍未知 |

复用已知 NPatch 组合为对照，不重复把它当作新发现的待支持框架。容器/虚拟化若改变目标身份或不能提供需要的 API，单独说明差异及是否值得另立适配；不自动带入 F18 产品级克隆，也不通过放宽授权或改包名绕过当前目标边界。

调查出口为候选列表、按框架/版本/模式保存的对照矩阵、已确认问题及后续适配建议。能否正式支持按实际证据决定，不能把“列入调查”写成“已支持”，也不保证所有候选最终适配。
