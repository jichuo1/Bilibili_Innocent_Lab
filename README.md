## 项目简介

Bilibili Innocent Lab 是一个面向 Android 哔哩哔哩客户端的 Xposed / LSPosed 模块。它在**尽量保持官方界面结构与操作习惯**的前提下，净化影响使用体验的内容，并补全评论、简介、播放器、外观与版本适配等方面的能力。

它**不是**独立的哔哩哔哩客户端，也不会替代官方应用：模块以运行时 Hook 的方式加载进目标应用进程，只对特定界面、数据绑定和交互入口做有限修改。账号、播放器、推荐、评论区和视频详情页仍是官方的，启用模块后按需开关即可。

| 设计取向 | 说明 |
| --- | --- |
| **可选择** | 绝大多数功能有独立开关且默认关闭，只开启需要的部分；实验性功能在设置里有明确提示 |
| **低侵入** | 只处理已适配、可明确识别的入口；识别不到就保留官方行为，不做猜测 |
| **可恢复** | 关闭开关并重启哔哩哔哩即恢复原样；设置可导出备份、预览后恢复 |
| **自适应** | 运行时版本适配、适配结果缓存与手动“重新适配当前版本”，降低客户端升级后整体失效的概率 |

> [!NOTE]
> 任何基于 Hook 的模块都无法保证永久兼容未来版本。使用前请阅读 Release 说明，遇到问题请按[问题反馈](#问题反馈)的流程提交。

## 快速开始

### 环境要求

| 项目 | 要求 |
| --- | --- |
| **Android 版本** | Android 8.1（API 27）及以上 |
| **Root / Hook 环境** | 建议使用 Magisk + LSPosed；也可[免 Root 加载](#免-root-支持) |
| **目标应用** | 官方 Android 哔哩哔哩，包名 `tv.danmaku.bili` |
| **模块框架** | Xposed / LSPosed 兼容环境 |
| **应用多开** | 仅支持**包名仍为 `tv.danmaku.bili`** 的系统级多用户 / 应用双开 / 工作资料；不支持改包名的克隆与 VirtualApp 类容器，详见[多开与多用户](#多开与多用户) |
| **已验证客户端** | 8.84.0～9.14.0 的主要版本路径 |
| **软件结构核查** | 云端 36 个准确 APK，覆盖 8.84.0～9.16.0；类/接口、成员签名、泛型和 R8 差异见[适配说明](docs/host-9.16.0-adaptation.md)。9.17.0 的 9170100 → 9170300 增量核查见[适配说明](docs/host-9.17.0-9170300-adaptation.md) |
| **漫游扩展** | 需要另行安装并启用兼容的哔哩漫游版本 |
| **预见式返回** | Android 14～15 提供开关；Android 16 及以上由系统强制启用，设置中不再显示该开关 |

> “已验证”只表示项目在相应版本或同类结构上进行过开发测试，不代表所有设备、系统主题、账号实验分组和客户端小版本都能得到完全相同的结果。介于已验证版本号之间的客户端理论上亦可使用，但不保证功能完全实现；若功能失效并希望项目适配，请按[问题反馈](#问题反馈)提交 Issue。

### 安装与启用

| 步骤 | 操作 |
| :---: | --- |
| **1** | 从 [GitHub Releases](https://github.com/jichuo1/Bilibili_Innocent_Lab/releases) 下载 APK，安装或覆盖安装模块 |
| **2** | 打开 LSPosed 管理器，启用 `Bilibili Innocent Lab` |
| **3** | 将官方哔哩哔哩 `tv.danmaku.bili` 加入模块作用域 |
| **4** | 强制停止哔哩哔哩，然后重新启动 |
| **5** | 打开模块设置，确认页面显示“**模块已激活**” |
| **6** | 在净化、增强、美化或实验性功能中开启所需选项 |
| **7** | 设置未立即生效时，使用模块内的“重启哔哩哔哩”，或手动强制停止目标应用 |
| **8** | 使用漫游扩展的话：首次构建或重建后，先检查缓存结果；已就绪时再按页面引导重启，已复用时无需为缓存再次重启 |

> [!TIP]
> - 可搭配哔哩漫游食用，本模块一并为其提供了高版本宿主兼容设置。若您使用本模块的“进阶设置”，请关闭其他模块中重复的功能以保证实现。

> - LSPosed 仓库中的版本可能存在滞后性。
> - **如果遇到启用模块后宿主冷启动时间过长的问题，或与宿主无法通信的问题，请尝试关闭 HMA-OSS 中对宿主的隐藏。**

> [!NOTE]
> 覆盖安装模块后，一般不需要清除哔哩哔哩数据。除非发布说明明确要求，否则不要随意清空客户端数据、模块配置或漫游缓存。

### ROOT 权限说明

若可能，请授予本模块 ROOT 权限，以实现以下功能：

- 保存设置后确认并重新启动哔哩哔哩。
- 统一诊断中心部分本地诊断内容。

> 本说明会跟随版本更迭即时修改，始终保证 ROOT 权限使用透明化；项目承诺不会滥用 ROOT 权限进行任何危害宿主设备的行为，详细参见项目最新开源代码。

### 推荐使用顺序

首次安装建议按以下顺序验证，逐项启用更便于判断问题来源，也能避免多个模块同时修改同一页面时难以定位冲突：

1. 确认模块已激活；
2. 只开启**一个**界面净化功能，重启哔哩哔哩并检查首页或详情页；
3. 测试评论区、简介与标题的自由复制，并按主题选择手动亮色气泡或自动跟随；
4. 基础功能稳定后，再尝试实验性功能；
5. 仅在已安装哔哩漫游且确有兼容需求时开启漫游扩展。

## 免 Root 支持

模块可通过补丁管理器加载到**本地修补**的哔哩哔哩客户端，不影响原有 Root / LSPosed 用法。目前支持两条路径：

| | **NPatch**（Manager 模式） | **LSPatch**（本地 / Manager 模式） |
| --- | --- | --- |
| **已验证范围** | B 站 8.90.2、固定修复版 833、签名等级 2、Android 16 / arm64 | B 站 9.13.0、签名等级 2、Android 16 / arm64（Debug 实机专项） |
| **版本下限** | 代码最低 Android 9；NPatch Manager 1.0.7 起 | JingMatrix LSPatch 1.2（487） |
| **集成（embed）模式** | ❌ 暂不支持 | ❌ 暂不支持 |
| **设置里的开关** | 选择“免 Root 支持” | 无需开启 NPatch 开关或通信兼容模式 |

> [!WARNING]
> **当前版本不支持集成（embed / `--embed`）模式**：该模式暂时关闭，以减少内嵌模块宿主的倒卖，相关实现保留；NPatch 与 LSPatch 共用同一个关闭开关。上表的版本下限不代表所有组合均已实测，支持范围以已验证组合为准。

### NPatch

1. 在 NPatch Manager 中添加并启用模块及宿主作用域；
2. 保留独立的模块设置 App，接受条款，选择“免 Root 支持”；
3. 冷启动哔哩哔哩，在模块界面验证回执。

- 启用后，NPatch 宿主优先通过**模块自己的鉴权通道**读取完整配置，不再要求开启“通信兼容模式”；Manager Remote Store 同步只是可选镜像，其不可用不影响直达配置就绪。
- 开启、关闭或修改相关设置后，需要**手动强制停止并重新打开**哔哩哔哩。只有取得当前授权并通过完整配置校验后，目标进程才会安装模块功能；模块界面收到并验证宿主回执后才显示为已激活。所有授权端点都不可达时，不会仅凭旧缓存启用功能。
- 设置 App 被系统强行停止后，请先打开设置 App，再冷启动哔哩哔哩。
- 覆盖安装设置 App 会保留现有配置；卸载重装会删除其配置、条款记录和账号授权，需重新接受条款并开启免 Root。业务设置可从“设置备份”导入，条款同意、授权凭据和运行回执不会随备份恢复，宿主仍需重新取得当前许可。仅卸载设置 App 不会移除已嵌入宿主的模块代码。

### LSPatch

1. 在 LSPatch 管理器中选择模块并点击“应用”（界面里的“本地”对应 `--manager`）；
2. 保留独立的模块设置 App，完成条款授权；
3. 冷启动哔哩哔哩验证。激活须通过当前授权配置及真实宿主回执确认。

已复现并修复 [issue #31](https://github.com/jichuo1/Bilibili_Innocent_Lab/issues/31) 所涉及的旧 NPatch 意图与 LSPatch 配置通道冲突；旧版 Legacy LSPatch、Canary 和矩阵外组合保持未验证。

## 多开与多用户

模块作用于哔哩哔哩的**包名**，因此“多开”能否使用，取决于克隆出来的那份客户端包名是否还是 `tv.danmaku.bili`。

| 多开形态 | 克隆后的包名 | 是否支持 |
| --- | --- | :---: |
| 系统多用户、应用双开、工作资料 | 仍为 `tv.danmaku.bili` | ✅ 需按下方步骤在**该用户下**单独启用 |
| 改包名克隆（部分免 Root 多实例、改包工具） | 变成其他包名 | ❌ |
| VirtualApp 类容器多开（分身类 App 内运行） | 容器 App 自己的包名 | ❌ |

**为什么改包名的克隆用不了**：模块的作用域固定为官方包名，管理器里无法手动添加别的包；即使框架肯注入，模块按官方包名解析的宿主资源与缓存目录也都会落空。这是有意的取舍——把宿主身份变成运行期变量会牵连授权链、调用方校验和跨进程广播，收益覆盖不到大多数用户。

**在分身 / 多用户下启用**：框架按 **Android 用户**分别投递服务，主用户里启用过并不会自动覆盖分身用户。

1. 在运行分身客户端的那个用户下，同样安装模块 App；
2. 在框架管理器里切换到该用户，为该用户启用本模块，并确认作用域包含哔哩哔哩；
3. 在该用户下打开一次模块设置，让配置完成发布；
4. 强制停止并重启该用户下的哔哩哔哩。

| 设置页提示 | 含义 |
| --- | --- |
| “当前 Android 用户 N 下没有框架服务” | 第 2 步没有在该用户下完成 |
| “模块在用户 A，哔哩哔哩在用户 B” | 模块和客户端装在了不同用户里，配置无法送达 |

诊断中心的「框架服务」一项会给出同样的判断依据。

## 功能介绍

模块把功能拆成独立开关，设置界面按下表组织；收藏与搜索可直达原有设置入口，已有开关值和生效方式保持一致。

| 界面入口 | 内容 |
| --- | --- |
| **常用** | 收藏的功能入口，复用原有开关值、权限和监听 |
| **净化** | 各页面的内容、广告、组件与提示过滤；跨页面共享的规则只保留一个入口 |
| **增强** | 评论 / 简介 / 标题复制、阅读与浏览交互、播放与完整数字等能力 |
| **美化** | 模块界面与宿主视觉、材质、背景及相关外观选项 |
| **模块** | 激活、诊断、更新和模块管理，以及实验性兼容与任务助手入口 |

> [!NOTE]
> **标记说明**：`默认开` 表示新装即开启，未标注的功能默认关闭；`实验` 表示仍在验证、效果因设备与客户端版本而异。除特别注明外，修改后需**重启哔哩哔哩**生效。若当前客户端没有可靠的适配入口，对应功能会跳过处理并保留官方行为。

#### 视频插帧 `实验`

用 GPU 生成中间帧，把 30 fps 视频补到 60 fps、25 fps 补到 50 fps，支持最高 4K 的视频。需先在设置中下载插帧模型。

- 超过屏幕分辨率的视频先缩到屏幕能显示的尺寸再处理，首次运行时的本机测速决定可持续的最高尺寸；HDR、受保护内容和不支持的帧率按原样播放；性能跟不上、或启用温控且设备过热时自动回到普通播放。
- 高分辨率会多一点延迟（音画仍同步），耗电也更多。
- 可设置**补帧帧率上限**（实际目标跟随系统真实输出的刷新率与本机可持续的性能），可开启**插帧状态提示**，也可关闭插帧温控（开启前需二次确认）。

#### 音频拯救 `实验`

处理当前视频的声音，默认关闭。

| 选项 | 说明 |
| --- | --- |
| 关音菩萨 · 防突发炸耳 | 声音突然暴涨时立即压制，并把采样峰值限制在 −6 dBFS，随后平滑恢复；独立于整体响度均衡，实际耳机音量仍需自行控制 |
| 声道 | 原样、单声道（左右混合送到双耳，反相声音可能抵消）、自动补声（持续只有一边响或另一边几乎听不到时补声） |
| 语音降噪 | 减轻讲话视频的底噪和环境干扰，可能改变音色；以音乐为主的视频建议关闭 |
| 人声清晰度增强 | 减轻背景音乐对讲话的遮盖，已包含降噪；适合 BGM 过大的讲话视频 |

语音降噪与人声增强需要额外文件（首次下载约 56 MB，也可导入离线文件），防爆音和声道修复无需下载；两者会增加约 33 毫秒延迟。多声道和音频直通暂不支持。

### 🌍 漫游版本支持扩展

用于配合已经安装并启用的哔哩漫游模块。它**不是**哔哩漫游的替代品，也不提供账号、解析服务器、访问密钥或网络代理服务。

当较新的哔哩哔哩客户端改变内部分析目标时，旧版漫游可能无法正常分析新版本。启用扩展后，模块会尝试修补已知问题，并协助漫游重建完整缓存，使其设置入口、页面定制等功能在已适配版本中继续工作：

- 缓存损坏、过期或客户端版本变化时重新分析，减少无意义的重复全量分析和冷启动等待；
- 在“我的”页面补充漫游设置入口；
- 在模块与漫游之间同步开关状态；
- 处理部分 MIUI / HyperOS 环境中的应用可见性与后台启动限制；
- 功能关闭后恢复相应原生行为，不留残余兼容状态。

> NPatch 833 下，宿主与漫游实际 APK 内容、版本及手动重建代次一致时，会复用或恢复已验证的分析缓存，仅重修补造成的安装时间变化无需重复全量分析；首次构建、内容改变、损坏或手动重建仍需分析。先在兼容设置中“检查 NPatch 漫游缓存”，收到已就绪回执后再通过现有重启引导继续；不会自动终止宿主，也不承诺所有环境一次启动。缓存就绪不代表漫游所有功能均已生效。

## 常见问题

| 问题 | 排查方法 |
| --- | --- |
| 模块显示未激活 | 确认 LSPosed 已启用本模块，作用域包含官方哔哩哔哩；修改作用域后重启目标应用，必要时重启设备 |
| 分身 / 双开里检测不到 libxposed 服务 | 框架按 Android 用户分别投递服务：需要在运行分身客户端的那个用户下也安装模块、在管理器中切到该用户并为该用户启用，然后打开一次模块设置。改包名的克隆和 VirtualApp 类容器不在支持范围内，详见[多开与多用户](#多开与多用户) |
| 开关已打开但功能没有生效 | 先强制停止并重启哔哩哔哩；刚升级客户端可尝试“重新适配当前版本”；漫游扩展首次分析后先检查缓存状态，再按就绪提示继续重启 |
| 评论长按没有出现自由复制气泡 | 确认评论自由复制开关已开启，且当前页面属于已适配的官方评论区；若只有少量评论失效，请记录评论类型、是否带图、是否为回复列表及客户端版本 |
| 使用自由复制后图片无法打开 | 当前版本已专门保护带图评论的媒体容器；请确认使用最新构建并彻底重启哔哩哔哩进程，仍可复现时请说明操作顺序及气泡关闭后到点击图片的间隔 |
| 气泡内无法选择或复制文字 | 确认没有其他模块同时 Hook 系统剪贴板、文本选择工具栏或 PopupWindow；部分厂商系统深度定制了文本选择组件，遇崩溃请提供系统版本和 crash 日志 |
| 首页轮播仍然出现 | 首页结构可能受账号实验分组影响；请提供客户端版本、首页样式截图和完整日志，避免只描述“功能无效” |
| 漫游扩展开启后仍然异常 | 请一并提供：哔哩哔哩、哔哩漫游、本模块、LSPosed（含分支）、Android / ROM 各自版本，缓存检查结果与重启次数，以及框架中目标主进程的相关日志 |
| 与其他模块冲突怎么办 | 多个模块同时修改评论区、视频详情页、剪贴板、主题属性或漫游缓存时可能产生执行顺序冲突；建议暂时关闭其他模块仅保留本模块复现，确认单模块正常后再逐个恢复 |

## 面向开发者

<details>
<summary><b>构建项目</b></summary>

<br>

仓库根目录和 Gradle 工程目录并不相同。Gradle 工程位于 `Bilibili_Innocent_Lab/`。

**构建 Debug APK**

Windows PowerShell：

```powershell
cd Bilibili_Innocent_Lab
.\gradlew.bat assembleDebug --console=plain --no-daemon
```

Linux / macOS：

```bash
cd Bilibili_Innocent_Lab
./gradlew assembleDebug --console=plain --no-daemon
```

**运行 JVM 单元测试**

```powershell
.\gradlew.bat testDebugUnitTest --console=plain --no-daemon
```

**运行 Lint**

日常迭代使用快速检查：

```powershell
.\gradlew.bat :app:lintFast --console=plain --no-daemon
```

快速检查与完整检查启用相同规则，区别仅在于报告目录和可同时运行的任务；测试源码由编译与测试任务验证，不纳入 Lint。提交前和 CI 使用完整检查：

```powershell
.\gradlew.bat :app:lintDebug --console=plain --no-daemon
```

快速报告保存到 `app/build/reports/lint/fast/`，完整报告保存到 `app/build/reports/lint/full/`，HTML 文件均为 `lint-results-debug.html`。使用完整任务名；`lintFast` 仅允许与 `assembleDebug`、`assembleDebugAndroidTest`、`testDebugUnitTest` 同时运行，其他任务和完整门禁分开执行。Linux / macOS 使用 `./gradlew` 执行相同任务。

本项目构建统一使用 `--no-daemon`，保留任务与依赖缓存；日常不随意 `clean`。缓存完整时可添加 `--offline`。

**产物校验**

调试 APK 输出位置：`Bilibili_Innocent_Lab/app/build/outputs/apk/debug/app-debug.apk`。

构建完成后，确认 Gradle 任务成功，并使用该次构建的 APK；`UP-TO-DATE` 或 `FROM-CACHE` 是有效的增量结果，不能仅凭 APK 修改时间判断产物是否包含最新输入。安装到设备后，建议对比本地 APK 与设备端已安装 `base.apk` 的 SHA-256，避免安装到旧产物。

运行架构与回归验证由本地技术档案维护，开发工作从本地 `AGENTS.md` 进入。

</details>

<details>
<summary><b>性能与兼容设计</b></summary>

<br>

本模块包含多个运行在目标应用进程中的 Hook，因此设计时尽量避免把复杂逻辑放入高频回调。

| 方面 | 做法 |
| --- | --- |
| **热路径与调度** | 滚动、触摸和文本绑定路径设置快速返回条件；评论绑定使用空闲调度与分批处理 |
| **缓存与生命周期** | 反射获得的方法和字段尽量缓存；页面、Dialog 和评论 View 使用弱引用保存；异步任务只持有 Application Context；新版本适配结果写入缓存，避免每次启动重复扫描 |
| **兼容与豁免** | 跨进程开关读取具有多级降级路径；对自己的 Dialog、系统选择句柄和宿主媒体容器设置身份或来源豁免；在 ROM 差异明显的窗口、状态栏和主题属性上使用显式配置 |

项目不会为了追求“拦截更多内容”而无条件接管所有系统 API。对于 PopupWindow、Dialog、剪贴板、广播和触摸事件等影响范围较大的入口，优先根据对象身份、调用来源和手势生命周期判断是否属于模块目标，避免干扰图片预览、系统文本选择和宿主其他正常功能。

</details>
